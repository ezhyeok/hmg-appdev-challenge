# rest-engine: 쉼표 판단 엔진

차에 탄 사람의 '주행가능시간'(다음 화장실·휴식이 필요해질 때까지 남은 시간)을 계산하고, 언제 무엇을 물을지 정하는 순수 Kotlin 모듈이다. 안드로이드에 의존하지 않아 JVM 단위 테스트로 시나리오를 검증한다. 앱(`app/`)은 composite build로 가져다 쓴다.

- 제품 사양: `docs/product/SPEC.md` 4장(판단 로직), 7장(시연 시나리오)
- 근거: `docs/research/ai-science.md` (아래 'AI §n'은 그 문서의 절 번호). 기본값마다 `CoachConfig.kt` KDoc에 출처를 적었다.
- 빌드·테스트 (repo 루트에서): `./gradlew -p rest-engine test`

## 1. 앱과 주고받는 것

| 호출 | 하는 일 |
|---|---|
| `CoachEngine(config, profile, memory, random, texts)` | 여정 하나당 하나. `random`은 톰프슨 샘플링용(테스트는 시드 고정), `texts`는 문구(상속해서 바꿀 수 있음) |
| `update(CoachInput): CoachOutput` | 1초 안팎마다. 게이지 2개, 운전 패턴, 다음 추천, 지금 물을 질문 1개, 공조 제안, 급해 결과 |
| `urgent(input)` / `plan(input)` | 급해 순위, 피트스톱 계획. 상태를 바꾸지 않는다 |
| `onPromptResult(id, accepted, now)` | 질문에 대한 응/아니 (음성이면 `VoiceIntent.Accept/Decline`을 다음 update에 넣어도 같다) |
| `noteAccepted(stop, purposes, now)` | 운전자가 화면에서 정차지를 직접 골랐고 내비 명령이 성공했다 (급해 목록, 계획 화면, 실패 뒤 다시 시도). 엔진이 물은 곳이 아니어도 된다. 아래 '들르기로 한 곳' |
| `setProfile(profile)` | 같은 `tripStart`면 이어 가고, 다르면 새 여정 |
| `memory()` | 기기에 저장할 개인 기록 (관측 간격, 질문 수락률) |

앱 연동 메모
- `CoachOutput.prompt`는 대답·만료 전까지 같은 id로 계속 나온다. 새 id일 때만 TTS로 말한다.
- 들르기로 한 곳: 질문을 수락했거나(`onPromptResult(id, true)`) 화면에서 직접 고른 곳(`noteAccepted`). 추천이 `NEXT_ACCEPTED`가 되고 그동안 엔진은 정차를 먼저 묻지 않는다. 후보 목록에서 1분 넘게 사라지면(지나침), 90분이 지나면, 화장실 정차·휴식이 기록되면 내린다(서 있는 동안에는 내리지 않는다). 그래서 앱은 그곳을 이후 update의 `candidates`에 같은 id로 계속 넣는다. `noteAccepted`는 같은 곳을 묻던 질문이 떠 있으면 그 질문을 수락한 것으로, 다른 곳을 묻던 화장실 질문(마지막 기회·급해 결과)은 그 선택으로 끝난 것으로 본다(무시로 치지 않아 쉼·시간당 횟수가 남지 않고, 늦게 온 대답도 받지 않는다). 사용자의 말("화장실 급해", "아이가 화장실 가고 싶대", "쉬고 싶어", "배고파", 주유)에 답할 곳이 바로 그곳이면 '들를까요?'를 다시 묻지 않고 "가휴게소에 들르기로 했어요. 6km 남았어요."(INFO)라고만 답한다. 그 뒤 그곳에 서면 '앱이 권해서 들른 정차'(0.5회)로 배운다. 첫 update 전에 불러도 된다(재시작 뒤 되살리기).
- 화장실 질문과 추천의 이유: 화장실 질문(`PromptKind.LAST_CHANCE`)이 떠 있는 동안 `CoachOutput.next`는 그 질문의 장소와 이유다(그 장소가 지금 후보에 있을 때). 화면은 질문 카드를 띄우는 틱의 `next.reasons`를 카드의 이유로 쓴다. 이유 코드: 마지막 기회 문구로 묻는 질문은 `LAST_CHANCE_CONGESTION`/`LAST_CHANCE_GAP`/`LAST_CHANCE_PREFERENCE`(+`LAST_CHANCE_GROUP`), 여유가 거의 없을 때의 가까운 화장실은 `NEXT_NEAREST_RESTROOM`, "화장실 가고 싶대"의 답은 `NEXT_REQUESTED_RESTROOM`, 수유·반려견 요청의 답은 `NEXT_REQUESTED_CARE`. 요청에 답한 곳이 마지막 기회이기도 하면 문장도 그 이유로 말하고 이유는 마지막 기회가 앞, 요청 코드가 뒤다(`[LAST_CHANCE_CONGESTION, NEXT_REQUESTED_RESTROOM]`).
- `candidates`는 매 update마다 지금 위치 기준 거리로 넘긴다(`routeDistanceM`, 없으면 `straightDistanceM`).
- `cabinAction = FRESH_AIR`는 사용자가 허용했을 때만 실행하고 1~2분 뒤 내기순환으로 되돌린다 (AI §1). 허용했으면 `cabinAutoAllowed = true`로 넘겨 질문을 생략한다.
- 출발할 때 "출발 전에 화장실 다녀오셨어요?"에 '아니/모름'이면 `lastRestroomAt`을 출발 60분 전으로 넣기를 권한다 (AI §9-1). 계약상 값이 없으면 출발 시각으로 본다.
- v0.2에서 추가한 필드(모두 기본값 있음): `Occupant.intervalOverrideMin`, `TripProfile.driverWakeAt`, `StopCandidate.walkDistanceM`, `CoachInput.rangeKm`, `CoachInput.cabinAutoAllowed`, `DrivingStyle.persistent`, `CoachOutput.cabinReason`, `PersonalMemory.restroomCensoredMin`, `PersonalMemory.restroomSuggestedMin`, `CoachConfig`의 여러 값. JSON 저장 시 `PersonalMemory`의 새 두 필드도 함께 저장해야 개인화가 정확하다.

## 2. 한 번의 update 흐름

```
신호(기어·차속·조향·제동·방향지시등·크루즈·문·공조) + 경로(남은 거리·시간·정체·다음 회전) + 후보 + 음성 의도
 → StopTracker            정차 판정: 화장실 정차(P 3분 + 문), 휴식(P 15분)
 → RestroomNeedModel      사람별 화장실 시계와 필요 곡선 → 화장실 게이지, 판단 마감
 → DrivingStyleAnalyzer   이번 주행 초반 대비 운전 패턴 편차 (보조 신호)
 → FatigueModel           휴식 리듬 시계 + 졸림 사전 곡선 → 피로 게이지
 → RouteContext·GapAnalyzer   경로 위 화장실 기회의 도착 시간 → 마지막 기회
 → UrgentRanker·PitStopPlanner  급해 순위, 정차 계획
 → PromptPolicy           지금 물어도 되는지, 무엇을 물을지 (하나만)
```

## 3. 모델별 설명

### 3-1. 정차 판정 (`StopTracker`)
- 기어 P가 3분 이상이고 그사이 문이 열렸으면 화장실 정차 → 모든 탑승자의 화장실 시계를 0으로. 정차 때 배뇨는 대개 요의 없이 기회가 와서 하므로(배뇨의 65%가 요의 없이, AI §3-A) 누구 때문에 섰든 모두 되돌린다.
- P가 15분 이상이면 휴식 → 휴식 리듬을 0으로 (도로공사 휴식포인트 15분 기준, AI §9-2).
- 기어 UNKNOWN은 차속이 3km/h를 넘을 때만 주행으로 보고, 아니면 직전 상태를 유지한다. update가 드물어 출발할 때야 문턱을 넘은 걸 알아도 그 순간에 사건을 낸다.
- 피로 시계와 질문은 '달린다는 것이 확인된' 때만: 기어 D·R·N, 또는 기어를 모르면 그 update에 잰 차속이 3km/h 초과. 차속은 그 update에 들어온 값만 쓴다(표본은 잰 지 5초 안). 예전에는 마지막 차속을 끝없이 들고 있어 신호가 끊긴 뒤에도 '주행 중'이었다.
- 기어 P는 차속보다 믿는다(P + 차속은 잡음이거나 몇 초 늦은 기어). P에서 나와 3분 안에 30km/h를 넘지 않고 다시 P면 같은 정차로 이어 센다(휴게소 안에서 옮겨 대기).

### 3-2. 화장실 필요 곡선 (`RestroomNeedModel`)
사람 i가 마지막 화장실 뒤 '필요해지는 시간' T를 와이블 분포(형상 k = 2.5 고정)로 둔다. θ = λ^k에 역감마 켤레 사전분포를 두면 사후예측 생존함수가 닫힌 식이다 (AI §8-1).

```
S(t) = (b / (b + t^k))^a          (t분까지 필요해지지 않을 확률)
Q(p) = (b · ((1 − p)^(−1/a) − 1))^(1/k)   (필요 확률이 p가 되는 시점)
사전: a0 = 3,  b0 = m0^k / (2^(1/a0) − 1)  → 사전 예측 중앙값이 프로필 중앙값 m0와 정확히 같다
갱신: 그 사람 때문에 선 정차·"급해" 요청  a += 1,   b += t^k
      앱이 권해서 들른 정차               a += 0.5, b += t^k   (권해서 들렀을 뿐일 수 있음)
      다른 사람 때문에 선 정차(중도절단)    b += t^k만            ('적어도 t는 버텼다')
```
- 3줄 설명: 사람마다 '필요해지는 시간'의 분포를 두고, 처음엔 배뇨일지 연구에서 나온 집단 중앙값으로 시작한다. 실제 정차 기록이 쌓이면 켤레 사전분포라 정수 몇 개(a, b)만 더해 갱신되고, 사건 3회면 개인 기록이 사전값과 같은 무게가 된다. 아직 필요해지지 않은 사람의 기록(중도절단)도 버리지 않고 '버틴 시간'으로 쓴다.
- 게이지(화면) = 탑승자 중 Q(0.5)까지 남은 분이 가장 짧은 사람의 값, `drivenBy` = 그 사람 (SPEC 4.1). 연료계처럼 1분에 1분씩 준다.
- 판단 마감 = 탑승자 중 누군가 필요해질 확률 1 − Π S_i(e_i + Δ)가 0.3에 닿는 Δ(상한·음성 요청 포함, AI §8-1·8-2). 마지막 기회와 피트스톱은 이 마감을 쓴다. 혼자면 그 사람의 Q(0.3) − e, 여럿이면 더 이르다(어른 둘 83분, 넷 63분). 게이지(가장 급한 한 사람의 0.5)보다 인원만큼 더 앞서므로, 한 사람만 봤다면 묻지 않았을 마지막 기회에는 이유 LAST_CHANCE_GROUP을 붙인다. 근거와 비교 수치는 SPEC 4.1, 테스트는 GroupNeedTest
- 정차 간 상한: 어르신·임신부 2시간(걷기 권고, CDC), 영아 2시간(카시트 관행 권고, 근거 제한적)은 확률과 상관없이 문턱의 상한이다.
- "아이가 화장실 가고 싶대" 같은 음성 요청은 그 사람을 바로 0(NOW)으로 올리고 사건으로 기록하며, 엔진이 바로 다음 화장실(진입로 2km 밖)을 답한다. 누구인지 모르면 말할 수 있는 사람(영아·반려견 제외) 중 가장 급한 사람으로 보고, 그런 사람이 없으면 아무에게도 기록하지 않는다(목록에 없는 운전자의 필요). 정차를 놓쳐 NOW에 갇히지 않게 2시간 뒤 푼다.
- 출발 뒤 프로필의 마지막 화장실 값이 바뀌면(사용자가 고침) 그 값을 따른다. 그 뒤 엔진이 기록한 화장실 정차가 있으면 정차가 이긴다.
- 문맥 보정(`docs/research/need-covariates.md`, SPEC 4.1): 시계를 유효 시간 τ로 돌려(τ += dt/m, S(t) = S0(τ), 기록도 τ) 닫힌 식을 그대로 쓴다. 식사 정차(`MealStopRule`: P 20분 + 음식 있는 곳·수락한 식사 정차·"배고파". 선 곳은 마지막으로 300m 안에서 본 후보로 알고, 그 뒤 2km 넘게 달렸으면 잊는다) 뒤 구간 ×0.8(20시 이후 ×0.9, 게이지와 마감), 밤(20~07시)에 잠든 아이(`CoachInput.asleepOccupantIds`의 CHILD) ×1.5(게이지에만). 이유 `RESTROOM_AFTER_MEAL`·`RESTROOM_ASLEEP`. 테스트는 ContextFactorTest(수식), ContextFactorEngineTest(정차·입력).

### 3-3. 운전 패턴 편차 (`DrivingStyleAnalyzer`) — 보조 신호
조향 신호에 대해 아는 것: 앞바퀴각일 수 있고 해상도를 모른다, Virtual Console과 부호가 반대다, 값이 안 바뀌어도 약 3초마다 같은 값을 다시 보낸다 (AI §1, 에뮬레이터 확인). 그래서 절대 각도 기준을 쓰지 않는다.
1. 60초 창, 정속 표본만: 70km/h 이상, 제동·방향지시등이 없고 그 뒤 10초가 지난 표본 (EU DDAW 70km/h, AI §9-2).
2. 준비 5분: 기준선에 넣지 않고 이 차의 조향 변화 크기(같은 값 반복을 뺀 |Δ각| 중앙값 s)를 잰다. 반전 gap = max(0.1도, 2s). 단위가 1/15로 작아도 같은 반전율이 나온다(테스트로 확인).
3. 특징 4개: 조향 반전율(방향이 gap 이상 바뀐 횟수/분, Markkula & Engström 방식), 조향 보정 크기(값이 바뀐 표본의 |Δ각| 평균), 정속 차속 표준편차(크루즈 꺼짐만), 급제동 수(8km/h/s 이상).
4. 기준선: 준비 뒤 정속 20분의 특징별 중앙값·MAD.
5. 점수: 강건 z = (x − 중앙값)/max(1.4826·MAD, 하한)을 [−2, 4]로 자르고, 가중 스토퍼 결합 `S_w = Σ w_j z_j / √Σ w_j²`(정상이면 대략 N(0,1)). 크루즈가 창의 절반 이상이면 조향 증거를 절반으로 줄인다(차로 유지 보조 개입을 알 수 없음).
6. 지수이동평균 `S ← 0.8·S + 0.2·S_w`, 관리한계 `UCL = 3√(λ/(2−λ)) = 1.0`. 편차 = clamp(S / 2UCL, 0, 1) → 0.5가 3σ 관리한계, 0.6부터 단계를 앞당길 수 있다.
7. 편차 지속: 최근 5개 창 중 3개 이상이 S_w ≥ 2 (AI §9-2 "5분 안 3회"). 단계를 앞당기려면 편차 ≥ 0.6과 지속이 모두 필요하다.
- 이유 문구: 가장 많이 벗어난 특징 하나 ("최근 10분 핸들 미세 조정이 평소보다 늘었어요"). 휴식하면 점수만 0으로, 기준선은 그 주행 동안 유지.

### 3-4. 피로 게이지 (`FatigueModel`)
두 시계 중 먼저 바닥나는 쪽까지 남은 분 (AI §8-3).
- 휴식 리듬 시계(시간-과업 피로): 마지막 15분 이상 휴식 뒤 연속 운전, 기본 2시간 (Highway Code, 국내 화물차 규정, 도로공사 권고). 운전한 1분을 가중해서 센다: 02~06시 ×2(연속 1시간이면 NOW, AI L1 규칙), 14~16시 ×1.2, 깨어 있은 지 17시간 이상 ×1/0.8, 크루즈 단조로움 ×1/0.9. 지난밤 수면 6시간 미만이면 2시간 기준 ×0.8, 5시간 미만 ×0.8². 경계에서 단계가 튀지 않게 적분하고, 남은 분은 앞으로의 가중을 따라가며 계산한다.
- 졸림 사전 곡선(Three-Process Model, Åkerstedt 2004): `KSS ≈ 10.6 − 0.6(S + C)`, `S = 2.4 + 11.9·e^(−0.0353·깨어 있은 시간)`, `C = 2.5·cos(2π(시각 − 16.8)/24)`. KSS가 6에 닿을 때까지 남은 분(1분 간격으로 24시간 앞까지). 07시 기상이면 자정 넘어 00:35 무렵 6에 닿는다. 기상 시각을 모르면 07:00(04~07시 출발은 출발 1시간 전, 00~04시 출발은 전날 07:00).
- 휴식은 시간-과업 피로만 줄이고 졸림은 못 없앤다(AI §2). 그래서 휴식은 리듬 시계만 0으로 하고, 졸림 곡선은 60분 뒤 다시 본다(카페인·짧은 낮잠 효과 약 1시간).
- 단계: 남은 30분 이하 WATCH, 20분 이하 SOON, 0 NOW(= 휴식 권고, AI의 L1). 운전 패턴 편차(0.6 이상 + 지속)는 한 단계만 앞당기고 NOW를 넘지 않는다.
- '강한 권고'(AI L2): "졸려" 또는 상태 확인 "응", KSS 사전값 ≥ 7, NOW + 강한 편차 지속(≥ 0.8). 이때는 쉬기만 하지 말고 커피 뒤 15분 이내 낮잠, 운전 교대를 권한다(카페인은 선택지로만).
- 질문 사다리: SOON 또는 편차 지속 → `CHECK_IN` "혹시 졸리세요?" → "응"이면 NOW + 강한 휴식 권유, "아니"면 20분 동안 패턴 편차를 피로에 넣지 않는다(본인 자기보고를 더 믿는다, AI §1). NOW → `REST_SUGGESTION`.
- 내기순환은 피로를 올리지 않는다. 30분 이상 + 공조 켜짐 + (탑승 2명 이상 또는 피로 SOON 이상)이면 `cabinAction = FRESH_AIR`와 편의 기능 이유(`cabinReason`)를 따로 낸다.

### 3-5. 마지막 기회 (`RouteContext`, `GapAnalyzer`)
- 입력: `InputSanitizer`가 NaN·무한대 거리·시간을 '모름'으로 바꾸고 그런 정체 항목을 뺀다. 정체 항목은 [0, 목적지]로 자르고 합집합으로 만든다(겹친 곳은 가장 느린 속도로 한 번).
- 도착 시간: 정체 밖은 자유 속도 v(내비 남은 거리·시간에서 정체 몫을 뺀 값, 없으면 현재 속도나 80km/h), 정체 구간은 '통과 시간 × 지나간 비율'. `도착(d) = (d − 앞쪽 정체 길이)/v + 앞쪽 정체 통과 시간`. 후보에 `etaS`가 있으면 교통 반영 값으로 보고 그대로 쓴다. 거리순으로, 엔진 계산 후보는 더 가까운 후보들의 가장 큰 지연(도착 − 엔진 계산)만큼 늦추고, 내비 ETA는 더 가까운 내비 ETA보다 이르지 않게만 올린다.
- 판단 범위: 후보 목록을 자른 곳(`candidatesUntilM`)과 목적지 너머 후보는 공백의 증거가 아니다. 그 앞 마지막 기회 뒤 공백은 자른 곳까지(아래 한계)나 목적지까지.
- 판단 마감 D(누군가 필요해질 확률 0.3)를 두고 세 규칙: (1) 게이지: D 안에 닿는 마지막 기회 다음이 D를 넘고 그 간격이 15분 이상이면 그곳(휴게시설 간격 기준 최대 25km ≈ 고속 15분, AI §3-C). D 안에 닿는 기회가 없으면(마감이 지났다) 진입로 2km 밖의 가장 가까운 기회로 같은 판단. 단 이때는 공백의 끝이 아는 다음 기회나 목적지여야 한다(자른 목록의 아래 한계만으로는 묻지 않는다: 목록이 빠짐없다는 약속이 틀리면 휴게소마다 울린다) (2) 정체: 통과 30분(민감 탑승자면 20분) 이상이고 안에 화장실이 없으면 정체 직전 기회. 사이에 기회가 없고 1km 안으로 이어진 항목은 한 정체. 단 정체 뒤 첫 기회(또는 목적지)가 D 안이면 묻지 않는다. 목록 범위 밖에서 시작하는 정체는 보지 않는다 (3) 커버리지: 과민성 방광 20분, 과민성장증후군 15분보다 긴 간격 앞 (절박감은 시간으로 예측할 수 없다, AI §3-A). 여러 개면 가장 먼저 정해야 하는 곳.
- 추천·질문 카드의 정차 후보에는 한 함수(`withEta`)로 이 도착 시간을 채운다(내비 ETA가 있으면 그대로).
- 질문은 진입로까지 2~5km일 때만 (`PromptPolicy`).

### 3-6. 급해 모드 (`UrgentRanker`)
`총 소요 = 주행(etaS 또는 거리÷평균 속도) + 주차·도보(주유소 1, 졸음쉼터 1, 휴게소 2, 공중화장실 2, 공영주차장 3 + 도보) + 유턴(필요 5, 모름 1)`. 순위 점수 = 총 소요 + 영업 여부 모름 3 − 야간(22~06시) 비상벨·CCTV 2 − 영아 동승 시 기저귀 교환대 3. 주차 불가·영업 종료·화장실 없음은 제외. 고속도로 졸음쉼터는 지침상 비상벨·CCTV가 기본 시설이라 데이터에 표시가 없어도 야간 가점(AI §3-C). 주행 중 2곳, 정차 중 5곳.

### 3-7. 피트스톱 플래너 (`PitStopPlanner`)
경로가 고정된 운전자 일정 문제(AI §8-4)를 동적 계획법으로 푼다.
- 노드: 출발, 후보(거리순), 끝(목적지, 없으면 마지막 후보). 상태 (마지막 정차 i, 주유 여부, 식사 여부) → 상태 4(n+1), 전이 O(n), 전체 O(n²).
- 구간 상한: 첫 구간은 min(지금 판단 마감, 피로 게이지), 정차 뒤에는 min(모두 방금 다녀온 상태의 판단 마감, 그 시각부터의 2시간 리듬). 넘친 시간은 '위반'으로 세어 불가능해도 가장 덜 어기는 계획을 낸다.
- 비용(사전식): 위반 → 정차 수 → 선호 감점(식사 시간대를 지나는데 식사 안 함 60, 영아인데 수유실·교환대 없음 15, 반려견 공간 없음 5) → 정차·우회·진출입 시간(진출입 5분이 정차마다 붙어 묶음 정차가 유리).
- 주유 위반은 주유 없이 '주행가능거리 − 50km'를 넘어 달린 거리를 구간마다 새로 넘은 만큼만 센다(예전에는 넘은 뒤 정차마다 다시 더해 화장실 계획이 틀어졌다). 메모는 주유 몫(`PLAN_FUEL_SHORT`)과 화장실·휴식 몫(`PLAN_GAP`/`PLAN_NOW`)을 나눈다.
- 목적 묶기: 화장실(항상), 휴식(90분 이상 운전 뒤), 식사(11:30~13:30, 17:30~19:30 + 음식), 주유(필요 + 시설), 수유, 반려동물. 정차 시간 = 목적별 시간의 최댓값(화장실 7, 휴식 15, 식사 35, 수유 25, 반려견 10분).

### 3-8. 묻는 타이밍 (`PromptPolicy`)
- 한 번에 하나. 45초 안에 대답이 없으면 내린다.
- 묻지 않는 때: 다음 회전 500m 안 또는 지금 속도로 30초 안, 최근 10초 안의 제동·방향지시등·큰 조향, 질문·음성 대화 뒤 30초(음성 작업 뒤 인지 분산이 최대 27초, AAA 2015). 사용자가 물은 것(급해, 얼마나 남았어, 쉬고 싶어)에는 바로 답한다.
- 같은 종류는 물은 뒤 20분 쉼, 거절하면 2배씩(40 → 60분 상한), 단계가 오르면 바로 풀림 (AI §9-3). 마지막 기회는 거절한 곳을 지나면 풀린다(SPEC 4.6). 환기는 60분.
- 시간당 3번. 같거나 높은 우선순위 질문만 센다(환기·상태 확인 셋이 마지막 기회를 막지 않는다). NOW 단계 질문은 상한에서 뺀다.
- 사용자가 말한 것(급해, 아이가 화장실, 쉬고 싶어, 배고파, 주유, 얼마나 남았어)에는 바로 답한다. 같은 때 둘이면 하나를 먼저, 나머지는 지금 질문이 끝난 뒤에. 사용자의 말에 끊긴 엔진 질문은 '무시'로 치지 않고 쉼·횟수를 되돌린다. 사용자 요청에 답한 정차를 거절하면 그곳을 지날 때까지 같은 곳을 다시 묻지 않는다.
- 질문 대상이 후보 목록에서 빠져도, 마지막으로 본 거리에서 150km/h로 달렸어도 아직 500m 밖이면 질문을 유지한다(목록 깜빡임).
- 질문 id는 엔진 인스턴스마다 다른 접두어(프로세스 시작 시각 기반) + 번호. 앱은 id가 바뀔 때만 말하므로 엔진을 다시 만들어도, 새 여정이어도 겹치지 않는다.
- 급한 질문(마지막 기회, NOW)은 우선순위가 낮은 활성 질문을 밀어낸다.
- 기어 P로 서 있는 동안에는 앞쪽 정차(마지막 기회·휴식 제안)와 상태 확인을 묻지 않는다. 휴식은 15분, 화장실 시계는 3분이 지나야 되돌아가므로 그 사이에 "다음 휴게소에 들를까요?"가 나오던 것을 효과 시뮬레이션에서 찾아 고쳤다.
- 묻는 거리 학습(톰프슨 샘플링): 질문 종류 × 거리 구간(마지막 기회 2~3/3~4/4~5km, 휴식 2~5/5~10/10~20km)마다 수락률 `Beta(1 + 수락, 1 + 거절)`. 대상마다 한 번 표본을 뽑아 가장 큰 구간의 상한 안에 들어오면 묻고, 결과는 실제로 물은 구간에 쌓는다. 기록이 없으면 고르게 탐색하고, 잘 받아들여지는 거리로 점점 모인다.

### 3-9. 문구 (`CoachTexts`)
질문은 '짧은 상황 설명 + 예/아니오 하나'. 조사(이/가, 을/를, 이에요/예요)는 받침으로 고른다. 앱은 상속해서 원하는 함수만 바꾼다. "감지"라는 말은 쓰지 않는다.

## 5. 하지 않는 것 (주장하면 안 되는 것)
- 졸음을 감지하거나 판정하지 않는다. 카메라·생체 신호가 없고, 인증 졸음경고장치도 최저 민감도 40%다. 조향 편차는 '이번 주행 초반과 다르다'는 보조 신호이고, 혼자서는 휴식 권고 단계를 넘기지 않는다.
- KSS를 추정한다거나 정확도를 말하지 않는다. TPM은 인구 평균 곡선이고, 우리 앱으로 검증한 데이터가 없다(에뮬레이터 신호는 합성).
- 방광 상태나 요의를 측정·예측하지 않는다. 시간·프로필·기록으로 확률을 추정할 뿐이다. 의료 진단·질환 관리 효과도 주장하지 않는다.
- "2시간마다 쉬면 졸음이 해결된다", "내기순환 CO2가 졸음을 일으킨다"고 말하지 않는다. 환기는 편의 기능이다.
- 휴게소 혼잡도나 정체 해소 시점을 예측하지 않는다. LLM은 판단하지 않는다(엔진은 결정적이다).

| 화면 게이지 | 조건부가 아닌 '필요 확률 0.5까지 남은 분'(연료계), 탑승자 최솟값 | AI §8-1은 조건부 중앙 잔여시간·묶음 확률을 제안. 사전예측분포의 조건부 잔여시간은 성인이 몇 시간이 지나도 약 47분 아래로 내려가지 않아 SPEC의 NOW 단계가 오지 않는다. 요의가 생겨도 말없이 참는 경우가 많아 '아직 말이 없다'를 증거로 쓰지 않았다. 판단(마지막 기회·계획)은 묶음 확률 0.3(아래 행) |
| 1명일 때 환기 | 피로 SOON 이상이면 1명이어도 권함 | AI §9-2는 2명 이상. SPEC 시나리오 2(혼자, 오후 졸음 → 외기 전환)를 지키되 졸음 원인이라고 말하지 않는다 |
| 시간당 상한 | NOW 단계 질문은 제외, 같거나 높은 우선순위끼리만 센다 | 응답 없는 낮은 단계 질문 몇 번이 정작 '지금 쉬기' 권고나 마지막 기회를 한 시간 막는 것을 테스트에서 확인 |
| 판단 마감 | AI §8-2대로 '누군가 필요해질 확률' 0.3 (묶음). 게이지는 한 사람 기준 그대로 | 한 사람 기준 마감(2026-11-11 감사 O6 수정 직후)은 어른 둘의 위기 비율을 12.0 → 14.1%로 올렸고, 게이지까지 묶음 기준이면 막히지 않는 길의 질문만 늘었다(SPEC 4.1의 비교). 감사가 짚은 '게이지가 넉넉한데 묻는다'는 이유 LAST_CHANCE_GROUP으로 화면이 설명한다 |
| 마지막 기회 게이지 규칙 | 간격 15분 이상일 때만 | 확률 규칙만 쓰면 9분마다 휴게소가 있어도 "지나면 9분 동안 화장실이 없어요"라고 묻게 된다 |
| 묻는 거리 | 2~5km (SPEC) | AI §9-3은 3~5km 첫 가용 창, 1.5km 안이면 포기. 톰프슨 구간이 둘을 함께 덮는다 |
| IBS 사전값 | 방광은 성인 값 + 커버리지 규칙 | AI §9-1은 'IBS 간격 모델 끔'. 장 절박감은 커버리지로, 방광 필요는 성인 곡선으로 나눴다 |
| 임신부·영아 | 3기 1.5시간, 수유 3시간(1~6개월) | 주수·월령 입력이 없어 보수적 값. `intervalOverrideMin`으로 바꾼다 |
| 단계 경계 20분 | SOON | SPEC 표의 '45~20 WATCH, 20~10 SOON'이 20을 양쪽에 포함해 안전한 쪽으로 |

## 7. 테스트
`src/test/kotlin/dev/shimpyo/engine/` — 컴포넌트별 단위 테스트(null 신호, 후보 없음, 기어 UNKNOWN, 시계 역행, 14시간 주행, 반복 조향 값, 단위가 다른 조향, 크루즈 등)와 SPEC 7장 시나리오 테스트(`ScenarioTest`):
1. 귀성길: 아이 동승 + 안성 뒤 40분 정체 → 진입로 2~5km에서만 "안성휴게소가 정체 전 마지막 화장실" → 거절하면 10분 동안 다시 묻지 않음 → 정체 속에서 아이 게이지가 NOW가 되면 다음 휴게소를 다시 물음
2. 오후 졸음: 14시대 + 조향 흔들림 → 상태 확인 → SOON + 환기 + 휴식 추천, "응"이면 커피·15분 낮잠 권유, "아니"면 패턴 편차 20분 제외
3. 밤 11시 급해 + 영아: 주차 가능·24시간·교환대·비상벨 화장실 1순위, 닫힌 곳·주차 불가 제외
4. 휴식 기록: P → 문 → 12분 → D에서 화장실 게이지 회복과 관측 기록 (피로는 15분 이상 쉬어야 회복)
5. 개인화: 짧은 간격이 반복되면 회차마다 게이지가 줄어든다 (150 → 133 → 122 → 114분)
6. 점심 피트스톱: 화장실 + 식사를 한 정차로 묶는다

## 8. 기획서 수치 (`runSim`)
`./gradlew -p rest-engine runSim` (여정 수: `-PsimTrips=500`) — `src/sim/kotlin`(main·test와 분리된 소스 세트)이 엔진 코드를 그대로 불러 두 파일을 쓴다. 시드가 고정이라 같은 명령이면 같은 파일이 나온다.
- `docs/plan/data/engine_curves.json`: 유형별 화장실 필요 곡선(사전예측 CDF, 게이지 0.5·판단 0.3 시각), 개인화(가상의 성인 12회 갱신 + 1,000명 앙상블, 중도절단 변형), 운전 패턴 편차(60분 주행, 분마다 EWMA·편차·지속·피로 단계), 피로 시계(13시 출발, 110분 휴식 유무).
- `docs/plan/data/effect_sim.json`: 경부고속도로 서울→부산 실제 휴게소·졸음쉼터 33곳 위에서 '지금처럼', '2시간마다 휴게소', '쉼표(실제 CoachEngine, 질문 수락 0.7·1.0)'를 탑승자 조합 5개 × 명절 정체 유무 × 사전값 오차(sigma 0.3·0)마다 여정 5,000개로 비교한다. 가정과 한계는 파일 안의 `assumptions`, `limitations`에 있다.
- 진단: `java ... SimMainKt <analysis.json> x trace 0 3`은 여정 몇 개의 사건 기록(필요, 질문, 대답, 정차)을 출력한다.
